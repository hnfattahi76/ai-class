سؤال ۱

فرق تابع معمولی با مدل یادگیری ماشین

برای محاسبهٔ کارمزد، بانک از قبل می‌داند چه قانونی باید اجرا شود. مثلاً اگر کارمزد یک‌هزارم مبلغ انتقال باشد، برای انتقال سه میلیون تومان، تابع سه هزار تومان برمی‌گرداند. نرخ کارمزد را بانک تعیین کرده و برنامه فقط آن را در فرمول می‌گذارد.

در تشخیص تراکنش مشکوک، خود مبلغ همیشه کافی نیست. مثلاً انتقال ۲۰ میلیون تومان ممکن است برای یک مشتری عادی باشد، ولی اگر از یک گوشی جدید، بعد از چند تلاش ناموفق برای ورود و به یک حساب ناشناس انجام شود، احتمال مشکوک بودنش بیشتر می‌شود. اگر بانک نمونه‌های کافی از تراکنش‌های سالم و متقلبانه داشته باشد، مدل می‌تواند از آن‌ها یاد بگیرد که هر نشانه چقدر اهمیت دارد.

وقتی مدل با نمونه‌های قبلی پارامترهایش را تنظیم می‌کند، در مرحلهٔ آموزش (Training) است. وقتی با همان پارامترها به یک تراکنش جدید امتیاز ریسک می‌دهد، در مرحلهٔ استنتاج (Inference) است.

سؤال ۲

مدل چطور از اشتباهش یاد می‌گیرد؟

ورودی ۱۰، وزن فعلی ۲ و جواب واقعی ۳۰ است.

  1. در Forward Pass مدل جوابش را حساب می‌کند. 2 × 10=20

  2. با Loss اندازهٔ اشتباه را حساب می‌کنیم. (20−30)²=100

  3. با Backpropagation از زیان به وزن برمی‌گردیم تا ببینیم تغییر وزن چه اثری روی زیان دارد. حاصل این حساب همان Gradient است.

    2(20−30) × 10=−200

    علامت منفی یعنی اگر وزن را کمی زیاد کنیم، زیان کمتر می‌شود.

  4. Optimizer با استفاده از گرادیان وزن را تغییر می‌دهد. مثلاً اگر نرخ یادگیری را 0.001 بگیریم، وزن جدید 2−0.001(−200)=2.2 می‌شود.

  5. با وزن جدید، پیش‌بینی ۲۲ است و زیان به (22−30)²=64 می‌رسد.

حتی اگر وزن را به ۳ برسانیم و خطای همین نمونه صفر شود، هنوز نمی‌دانیم مدل روی نمونهٔ تازه چطور کار می‌کند. مثلاً اگر ورودی تازه ۲۰ و جواب واقعی ۵۰ باشد، مدل با وزن ۳ جواب ۶۰ می‌دهد. برای همین باید مدل را روی داده‌هایی امتحان کنیم که موقع آموزش ندیده است.

سؤال ۳

مدل زبانی چطور درخواست ساخت API را می‌فهمد؟

وقتی می‌نویسیم «یک API برای ثبت پست در ASP.NET Core طراحی کن»، اول متن به تکه‌های کوچک تقسیم می‌شود. به این کار Tokenization می‌گویند. هر تکه یک شماره به اسم Token ID دارد. مدل هر شماره را به یک بردار، یعنی مجموعه‌ای از عددها، تبدیل می‌کند تا بتواند آن را پردازش کند. به این بردار Embedding می‌گویند.

مدل کلمهٔ «پست» را کنار بقیهٔ درخواست می‌بیند. وجود API و ASP.NET Core کمک می‌کند آن را به معنی یک مطلب در برنامه بگیرد. این اطلاعات بخشی از Context یا زمینهٔ درخواست‌اند. بعد مدل احتمال توکن بعدی را حساب می‌کند، یک توکن به جواب اضافه می‌شود و این کار ادامه پیدا می‌کند تا پاسخ کامل شود.

مثلاً مدل ممکن است مسیر POST /api/posts را پیشنهاد بدهد، درحالی‌که همهٔ مسیرهای پروژهٔ ما با /api/v1 شروع می‌شوند. مدل از خودِ درخواست نمی‌تواند این قرارداد را بفهمد. اگر عامل یک endpoint مشابه از مخزن بخواند و در اختیار مدل بگذارد، مدل می‌تواند از الگوی همان پروژه استفاده کند.

سؤال ۴

چرا عامل متدی پیشنهاد داده که وجود ندارد؟

اول باید ببینیم پروژه واقعاً از چه نسخه‌ای از کتابخانه استفاده می‌کند. شاید عامل نمونه‌ای از نسخهٔ جدیدتر دیده باشد، متد را با متد یک پکیج دیگر اشتباه گرفته باشد یا اسم آن را از روی اسم متدهای مشابه حدس زده باشد. گاهی هم متد وجود دارد ولی در فضای نام دیگری تعریف شده و پروژه به آن دسترسی ندارد.

با Prompt Engineering دستور را مشخص می‌کنیم. مثلاً می‌گوییم «قبل از استفاده از این متد، بررسی کن در نسخهٔ نصب‌شده وجود دارد.» با Context Engineering اطلاعات لازم برای این بررسی را می‌دهیم، مثل فایل پروژه، نسخهٔ دقیق پکیج و متن کامل خطای Build. بعد اسم و ورودی‌های متد را در مستندات رسمی همان نسخه بررسی می‌کنیم. در مرحلهٔ Validation روی خود پروژه Build می‌گیریم تا ببینیم کامپایلر فراخوانی را قبول می‌کند یا نه. اگر رفتار متد هم مهم باشد، آن را با تست بررسی می‌کنیم.

«لطفاً دقیق‌تر باش» به‌تنهایی کافی نیست، چون به عامل نمی‌گوید باید کدام نسخه را بررسی کند یا از کجا بفهمد پیشنهادش درست است.

سؤال ۵

چطور همهٔ تست‌ها سبزند ولی قانون انتشار رعایت نشده؟

در BlogSpecLab ممکن است عامل فقط امتحان کرده باشد که «پست تأییدشده منتشر می‌شود». برنامه‌ای که هر پستی را منتشر کند هم همین تست را پاس می‌کند. برای پیدا کردن باگ باید حالت ممنوع را هم امتحان کنیم، یعنی نویسنده بخواهد پست تأییدنشدهٔ خودش را منتشر کند.

مرحله کاری که در این مثال انجام می‌دهیم
Specify می‌نویسیم که انتشار پست بدون تأیید ویراستار باید رد شود و وضعیت پست تغییر نکند.
Clarify روشن می‌کنیم بعد از تأیید ویراستار چه کسی اجازهٔ انتشار دارد.
Plan تصمیم می‌گیریم تأیید ویراستار سمت سرور بررسی شود تا حتی درخواست مستقیم به API هم از این شرط عبور کند.
Tasks کار را به اضافه کردن شرط انتشار و نوشتن تست برای حالت مجاز و ممنوع تقسیم می‌کنیم.
Implement شرط را در کد می‌گذاریم و با حساب نویسنده مستقیماً API را صدا می‌زنیم. بررسی می‌کنیم درخواست رد شود و پست در پایگاه داده همچنان منتشر نشده باشد.

سبز بودن تست‌ها یعنی برنامه در حالت‌هایی که امتحان کرده‌ایم طبق انتظار عمل کرده است. در این سؤال، اگر تست انتشار بدون تأیید را ننوشته باشیم، سبز بودن تست‌ها چیزی دربارهٔ رعایت آن قانون به ما نمی‌گوید.
